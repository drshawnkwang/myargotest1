# Individual Applications

Nearly all software is deployed via ApplicationSets in `argocd-applicationsets/`:

- `appset-helm.yaml` — PE toolset Helm charts, every cluster
- `appset-manifests.yaml` — PE toolset configs, every cluster
- `appset-oneoffs.yaml` — software on specific clusters

This directory is reserved for Applications that must NOT be generated by an
ApplicationSet. Currently that is a single case:

- `argocd.yaml` — ArgoCD manages its own Helm release. Generating it from an
  ApplicationSet means a bad AppSet edit can break the controller that
  reconciles it. Keeping it hand-written keeps the recovery path short.

This is a bootstrap-safety argument specific to self-management. It is not a
general preference for Applications over ApplicationSets.

Do not add software here simply because it is deployed to one cluster. Use
`appset-oneoffs.yaml` for that.

## Decision rule

| Situation | Where it goes |
| --- | --- |
| Fleet-wide chart | `appset-helm.yaml` |
| Fleet-wide config manifests | `appset-manifests.yaml` |
| Specific clusters | `appset-oneoffs.yaml` |
| ArgoCD itself | here, `argocd.yaml` |

## Status

`argocd.yaml` does not exist yet. ArgoCD on `kargo1` is currently not
self-managed from this repo, and this repo contains no ArgoCD Helm values file
(`AGENTS.md` references `argocd-values.yaml` at the repo root; it is absent).

Two things must be settled before adding it:

1. Locate the real source of ArgoCD's own configuration.
2. Note that `root-argocd-app.yaml` currently syncs only
   `argocd-applicationsets/`. This directory is **not** synced. Adding
   `argocd.yaml` requires either extending the root app to a second source or
   applying it manually — the latter being more consistent with the
   bootstrap-safety rationale above.

See `plans/05-appset-boundaries.md` (R2).
